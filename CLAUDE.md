# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This repo is unofficial documentation for the Kickbase fantasy-football API v4, plus an MCP server that exposes that API as tools for AI assistants. It has two independent parts:

- **Root** — static API documentation assets: `kickbase-v4.postman_collection.json`, `kickbase-v4.swagger.json`, `openapi_spec.json`/`.yaml`, and `docs/` (the hosted Swagger UI site at kevinskyba.github.io/kickbase-api-doc). These are hand-maintained exports, not generated by a build script in this repo — if you add/change an endpoint, update the Postman collection and Swagger/OpenAPI files to match.
- **`mcp-server/`** — a TypeScript MCP server (Node, `@modelcontextprotocol/sdk`) that wraps the Kickbase API as MCP tools. This is where almost all code changes happen.

Kickbase itself is not documented anywhere officially — endpoint behavior here is reverse-engineered, so response shapes use short/undocumented keys (`pim`, `uoid`, `ofs`, `mv`, ...) and can change without notice.

## Commands (mcp-server/)

All commands run from `mcp-server/`:

```bash
npm install
npm run build   # tsc -> dist/
npm run dev     # tsx src/index.ts (no build step, for iterating)
npm start       # node dist/index.js (requires a prior build)
```

There is no lint script and no automated test suite. The only test artifact is `test.ts`, a manual smoke script that hits the real Kickbase API using credentials from `mcp-server/.env`:

```bash
npx tsx test.ts
```

To manually exercise the MCP server over stdio (e.g. to check a new tool's schema or a live response), spawn `dist/index.js`, send an `initialize` request, then a `tools/list` or `tools/call` JSON-RPC request over stdin — there's no MCP Inspector config in the repo, but this raw-stdio approach works for quick checks.

## Architecture (mcp-server/)

Built on the MCP TypeScript SDK's modern `McpServer` / `registerTool` API (not the older `Server` + manual request-handler pattern). Every tool's input is validated at runtime with a Zod schema and carries `readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint` annotations.

```
src/
├── index.ts     # McpServer setup; imports and calls each register*Tools(server)
├── schemas.ts   # Shared Zod field schemas (leagueId, playerId, pagination, ...)
├── format.ts    # registerApiTool() — shared error handling + response truncation
├── auth.ts      # Login/token refresh/caching
├── client.ts    # HTTP client: response caching, request coalescing, image-field stripping
└── tools/       # One file per domain (leagues, market, players, lineup, ...),
                 # each exporting a register*Tools(server) function
```

Key design decisions to preserve when extending this server:

- **Tool outputs are untyped JSON passed through from Kickbase**, not encoded as Zod `outputSchema`s. The API's response shapes are undocumented and can change without notice, so a strict output schema per endpoint would be brittle for little benefit. Only tool *inputs* are validated.
- **`auth.ts`** handles login (`KICKBASE_EMAIL`/`KICKBASE_PASSWORD`) and token refresh transparently; `KICKBASE_TOKEN` bypasses login entirely if set. `client.ts`'s `withRetry` forces a fresh login and retries once on a `401` (unless a static token is in use).
- **`client.ts` payload slimming**: `stripImages()` drops any string value matching an image-path/URL shape, regardless of key name, since Kickbase responses are ~26-50% image paths that are useless to an AI client. Set `KICKBASE_KEEP_IMAGES=1` to disable this (e.g. building a UI on top of the server).
- **`client.ts` GET caching**: only slow-moving/historical data is cached (`/competitions`, `/matchdays`, `/table`, competition players, `/base/stage`, plus per-player `performance`/`transferHistory`/`marketValue`) — never budgets, market, lineup, or the live per-league player endpoint. Default TTL is 1h (`KICKBASE_CACHE_TTL`, seconds, `0` disables). Since Kickbase recalculates market values daily in a ~22:00-22:10 local-time window, the cache also force-flushes once on the first GET seen after 22:10 each day, so an hour-long TTL can't serve stale pre-recalculation `mv`/market-value data past that point. Any `POST`/`DELETE` flushes the whole cache via `flushCache()`, so a write is always followed by fresh reads. Identical in-flight GETs are coalesced into a single request.
- **`format.ts`'s `registerApiTool()`** centralizes try/catch → `isError` content and truncates responses over `CHARACTER_LIMIT` (25k chars) with a message pointing the caller at pagination/filter params — individual tool files should stay declarative (schema + one API call) and not duplicate this.
- Adding a new endpoint: add it to the relevant `src/tools/*.ts` file (or create a new domain file and register it in `index.ts`), following the existing `registerApiTool(server, name, { title, description, inputSchema, annotations }, fn)` pattern. Also add it to the tools table in the root `README.md`.

### Kickbase API quirks worth knowing before touching market/offer tools

- There is no `GET` for market offers — `/v4/leagues/{id}/market/{playerId}/offers` is `POST`-only (placing a bid). Open offers are instead read via `GET /v4/leagues/{id}/players/{playerId}/transfers` (`kickbase_list_player_offers`), which returns `ofs[]` plus market context (`iotm`, `iposl`, `mv`, `prc`). Don't confuse this with `/transferHistory`, which is *completed* transactions.
- `offerId` (as accepted by `kickbase_accept_offer`/`kickbase_decline_offer`) has been observed to equal the bidding user's ID (`u`/`uoid`), not a separate offer identifier.
- Kickbase removed visibility into competing bids on players you don't own — for a listing by another manager, `ofs[]` contains at most your own bid, never other managers' bids, even if you've been outbid. Full `ofs[]` visibility (all incoming bids) only applies to players you've listed yourself. An empty or single-entry `ofs[]` on someone else's listing is expected, not a bug.
- `kickbase_get_market` already includes `ofs[]` inline per listing (plus `unm`, the bidder name, which the single-player endpoint omits) — prefer it over `kickbase_list_player_offers` when scanning the whole market.
